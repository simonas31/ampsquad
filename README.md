# AmpSquad

Marketing website with an admin panel for AmpSquad ([ampsquad.lt](https://ampsquad.lt)).
Public pages are bilingual (Lithuanian by default, English under `/en`). Content is managed in the admin panel at `/admin`.

## Stack

- PHP 8.5, Laravel 13
- Filament 5 (admin panel) on Livewire 4
- Inertia 3 with React 19 and TypeScript for the public site
- Vite 8 and Tailwind CSS 4
- MySQL 8.4 (Laravel Sail locally)
- Spatie packages: media library, translatable, settings, sitemap
- PHPUnit 12 for PHP tests, Vitest for TypeScript unit tests

## What it does

- Public site: home page, projects portfolio, price calculator, contact form, CMS-managed static pages, and a shop with a product catalog (search, category, manufacturer, stock and price filters).
- Admin panel (Filament): projects, categories, tags, pages, videos, calculator capabilities, contact requests, notification recipients, shop products, catalog imports, and site settings.
- Contact form submissions are stored and emailed to the configured recipients through the queue.
- `/robots.txt` is served by a route; `/sitemap.xml` is generated by `php artisan app:generate-sitemap` (scheduled daily and run on every deploy).

## Local development

The project runs in Docker through Laravel Sail. Prefix PHP, Artisan, Composer and Node commands with `vendor/bin/sail`.

```bash
cp .env.example .env
# in .env set DB_CONNECTION=mysql, DB_HOST=mysql, DB_PORT=3306 and DB_DATABASE, DB_USERNAME, DB_PASSWORD (Sail creates the database from them)

vendor/bin/sail up -d
vendor/bin/sail composer install
vendor/bin/sail artisan key:generate
vendor/bin/sail artisan migrate --seed
vendor/bin/sail npm install
vendor/bin/sail npm run dev
```

- Site: http://localhost
- Admin panel: http://localhost/admin, signing in as `admin@ampsquad.test` with password `password`.
  `AdminUserSeeder` uses fixed credentials for local development only; never run it in production.
- Queued work (contact-form mail, image conversions, catalog imports) needs a worker locally: run `vendor/bin/sail artisan queue:work`.
- `migrate --seed` also fills the shop with about 5,000 demo products (local environment only, about a minute), made by running a catalog file through the importer. Afterwards it plays the admin (restocks, sells out and switches off some products), imports a changed file and checks that none of that was undone. Re-seed from scratch with `vendor/bin/sail artisan migrate:fresh --seed`.

## Product catalog import

Products are loaded from a JSON file in one fixed format, the *canonical catalog*. Nothing else is accepted: a supplier's XML, CSV or price list is converted to this format first (see [Converting other formats](#converting-other-formats)), and the import then treats every source the same way. The template is [resources/catalog/catalog.template.json](resources/catalog/catalog.template.json); it is also available from the **Download template** button on the admin Products list.

### Running an import

- **Admin panel:** Shop → Products → **Import catalog**, then pick the file. The import runs on the queue, so a worker must be running. Progress, counts and the problems found in individual products are on Shop → **Catalog imports**.
- **Command line:** `vendor/bin/sail artisan app:import-catalog path/to/catalog.json` runs it right away and prints the result. Add `--queue` to queue it instead.

A file of about ten thousand products takes roughly a minute the first time and about twenty seconds when nothing has changed. Importing the same file again is always safe.

### The file

```json
{
  "schema_version": 1,
  "products": [
    {
      "sku": "EXAMPLE-001",
      "name": "Example product name",
      "category": ["Top level category", "Sub category", "Leaf category"],
      "excerpt": "One plain-text sentence shown on product cards. 255 characters at most.",
      "description": "First line of the plain-text description.\nSecond line.",
      "price": "19.99",
      "stock": 5,
      "image_url": "https://example.com/images/example-001.jpg",
      "manufacturer": "Example Manufacturer",
      "ean": "5901234123457"
    }
  ]
}
```

`products` repeats once per product. Optional keys may be `null` or left out; unknown keys are ignored.

| Key | Required | Type and rules | Stored in |
|---|---|---|---|
| `sku` | yes | Text, 1 to 64 characters. The key a product is matched on. | `products.sku` (unique) |
| `name` | yes | Plain text, up to 255 characters. | `products.name`, both languages |
| `category` | no | List of names from the top level down, at most 8 deep, e.g. `["Tinklo įranga", "Komutatoriai"]`. Not a slash-separated string. | `product_categories` tree, `products.product_category_id` |
| `excerpt` | no | Plain text on one line, up to 255 characters. Shown on product cards. | `products.excerpt`, both languages |
| `description` | no | Plain text up to 5000 characters; `\n` separates lines. | `products.description`, both languages |
| `price` | yes | A decimal **string** with a dot and one or two decimals: `"19.99"`, `"20"`. From `0.01` to `100000.00`, in euros. A JSON number is refused, because floats round. | `products.price_cents` |
| `stock` | no | A whole number, `0` or more (JSON integer, not a string). The starting stock of a product the import **creates**; ignored for a product that already exists. Left out means `0`. | `products.stock_quantity`, new products only |
| `image_url` | no | An absolute `http` or `https` URL, up to 500 characters. | `products.image_url` |
| `manufacturer` | no | Text, up to 255 characters. | `manufacturers`, `products.manufacturer_id` |
| `ean` | no | 8 to 14 digits, as text. Not unique: variants can share a barcode. | `products.ean` |

**Text is plain.** A product whose `name`, `excerpt` or `description` contains HTML tags (`<li>`, `<br>`, `<div>`, ...) or character references (`&amp;`, `&#43;`, `&nbsp;`) is refused, so shoppers never see markup. Strip tags and decode references when converting.

### What the import does

- **Matching:** products are found by `sku`, ignoring case and accents (the database's own comparison). An unknown SKU creates a product; a known one is updated.
- **What the file owns:** name, excerpt, description (the same text goes into both languages, since catalogs are Lithuanian only), price, EAN, image link, category and manufacturer are overwritten on every import.
- **What the shop owns:** the stock quantity, `is_active`, an uploaded featured image, and the URL slug are never touched by an import. The file's `stock` only gives a **new** product its starting quantity; after that the quantity is managed in the admin panel (and, later, by orders), so a re-import can neither restock nor sell out a product. A product that has been on sale keeps its slug when it is renamed.
- **New products** are created **inactive**, with the file's stock (`0`, so sold out, when the file has none). Nothing reaches the shop until an admin switches it on: in Shop → Products, filter by *Active: no*, select, and use the **Activate** bulk action. Later imports never change whether a product is active.
- **Unchanged products** are not written at all, so `updated_at` and the sitemap's `lastmod` only move when something really changed. A file that differs only in `stock` changes nothing.
- **Missing products:** a product that is not in the file is left exactly as it is. Nothing is deleted or deactivated by an import.
- **Deleted products:** a product deleted in the admin panel is still updated by the file but stays deleted.
- **Repeated SKU in one file:** the last one wins; the earlier ones are reported as skipped.
- **Categories** are created as needed and matched on the whole path by their Lithuanian name, ignoring case, so "IP kameros" under two different parents stays two categories. **Manufacturers** are matched by name, ignoring case.
- **Images are linked, not downloaded.** A product with an uploaded image shows the upload; otherwise it shows `image_url` straight from the supplier's site. If that link is missing or fails to load, the shop shows a placeholder icon. Prefer `https` links: browsers may block or upgrade `http` images on an HTTPS site.
- **Products made by hand** in the admin panel have no SKU and are never matched or changed by an import.

### When something is wrong

- **The whole file is refused** (nothing is written) if it is not valid JSON, has no `schema_version` of `1`, has no `products` list or an empty one, is larger than 50 MB, or cannot be read. The reason is shown on the import's page.
- **A single product is skipped** (the rest are imported) if it breaks a rule above. The import's page lists the first 200 skipped products with their position in the file, SKU and every problem found; the skipped count covers all of them.
- **A crash or timeout** mid-way leaves the products already saved in place. Products are written in chunks of 200, each in its own transaction. Run the file again to finish: it picks up where it stopped.
- Only one import runs at a time. A second one fails right away with a message saying so.
- Import records, and the uploaded files kept for troubleshooting, are deleted after 90 days by the daily `model:prune`.

### Database

| Table | Purpose |
|---|---|
| `products` | Includes `sku` (unique, nullable), `ean` (indexed), `stock_quantity` (not null, default `0`), `image_url`, `product_category_id` and `manufacturer_id` (both nullable, set to null if the target is deleted). There is no manual sort order: the shop lists by availability and name, and the admin list by newest. |
| `product_categories` | The shop's own category tree: `parent_id`, translatable `name` and `slug` (unique per language). Separate from `categories`, which classifies portfolio projects. |
| `manufacturers` | `name` (unique). |
| `catalog_imports` | One row per import: uploader, filename, stored file, status, counters, the first 200 row errors, and why a whole file failed. |

`stock_quantity` is never empty: `0` means sold out, which is also where every new product starts until someone stocks it. Hand-made products need a stock number too.

### In the shop

The listing at `/shop` is filtered by query parameters, so every view has a shareable URL: `q` (words to find in the name, SKU or exact EAN), `category` (slug; includes sub-categories), `manufacturer` (id), `in_stock=1`, `min_price` and `max_price` (euros), and `sort` (`availability`, `price_asc`, `price_desc`, `name`, `newest`). Values that make no sense are ignored. Filtered and sorted pages are marked `noindex`.

A sold-out product stays visible with an "Out of stock" marker and cannot be added to a cart. A cart holds at most 100 different products, and a line cannot be set above the stock. If the stock falls below what a line holds, the line is flagged and counts only what is left, and the stored quantity is corrected the next time the visitor changes it (viewing a cart never rewrites it). A line whose product sells out is flagged and left out of the totals. The default order puts what can be bought first, then goes alphabetically.

### In the admin panel

Shop → Products is built for thousands of products: 10 to 100 rows per page (never "all"), newest first, and sortable by name, SKU, price and stock. The search box finds words in the name (in the language the list is showing), the SKU and the exact EAN; filters cover category (with sub-categories), manufacturer, stock, active, catalog or hand-made, and deleted. Every admin table shows its filters above the rows and applies them as they are chosen. Search and filters are remembered for the session.

- **Stock is edited in the list.** Click the number, type, press Enter. The product form keeps it in its own "Managed in the shop" section together with the active switch and the uploaded photo, which an import never changes. Everything in "Product data" (name, texts, price, SKU, EAN, category, manufacturer, image link) belongs to the import for products with a SKU.
- **Bulk actions** work on a selection or on every product that matches the filters ("select all"): activate, deactivate, set stock, delete, restore. They run as one update per 200 products and leave slugs and everything else alone.
- There is no manual product order and no "show everything" page size, on purpose.

### Converting other formats

Whatever produces the file (a script, a spreadsheet macro, a person) should follow the template and these rules, which the first conversion, from a supplier's XML feed, used:

- Strip HTML to plain text: turn list items, paragraphs and `<br>` into line breaks, drop other tags, then decode character references (in that order, so a literal `&lt;` survives as `<`).
- Split the category path into a list of names and drop the feed's root segment (`/Main/`).
- Write the price as a string exactly as the feed has it; never go through a float.
- Make `stock` a non-negative integer (negative counts become `0`).
- Cut excerpts to 255 characters at a word boundary.
- Use `null` for empty values, and keep one product per SKU (the last one if the feed repeats it).
- Leave out what the format has no place for. The feed's weight was dropped, since the shop has no shipping.

### Operations

- A queue worker must be running. In production it is the Supervisor program in [deploy/README.md](deploy/README.md), which also explains why `DB_QUEUE_RETRY_AFTER` must be `1900` (the import job's timeout is 1800 seconds).
- The upload goes through PHP, so `upload_max_filesize` and `post_max_size` must be at least 50M on the server. Sail already allows 100M; the production default of 2M does not.

## Tests

The PHP tests need MySQL (the migrations use MySQL-only JSON generated columns), so run them through Sail:

```bash
vendor/bin/sail artisan test --compact     # PHPUnit
vendor/bin/sail npm run type-check         # TypeScript
vendor/bin/sail npm test                   # Vitest
vendor/bin/sail bin pint --dirty           # code style
```

The feature tests render the Inertia pages, so build the assets once first (`vendor/bin/sail npm run build`) on a fresh checkout.

## Deployment

Pushing to `master` runs the GitHub Actions pipeline in [.github/workflows/deploy.yml](.github/workflows/deploy.yml). It runs the tests, builds the assets, and deploys to the production server (CloudPanel on Hostinger) over SSH.

Server setup, required secrets, the Supervisor queue worker and scheduler, rollback, and troubleshooting are in [deploy/README.md](deploy/README.md).
